なぜ 今 「LINE 単体では 訪日客は 取れない」 のか

訪日インバウンド客の 大半は LINE を 日常使用していません。 現状の「LINE で 予約 対応」 導線 は、 実は 国内リピーター (帰任 外国人・日本人 リピート) だけに 届いています。 3つの 構造的 ギャップ が 残ります。

GAP 01 — チャネル分断

訪日客の 主要 messenger は 国別に 完全分断

英語圏: WhatsApp / Instagram DM ・ 中華圏: WeChat ・ 韓国: KakaoTalk。 LINE 1本 では 全体の 2〜3割 しか 拾えず、 残り 7割は 問い合わせ 経路 が ない まま 離脱。

GAP 02 — 予約UI

日本語のみ の 予約フォームは 訪日客の 9割 が 離脱

Google Business や TripAdvisor 経由で 訪れても、 予約ページが日本語だけで 決済も現金前提だと、 その場で 競合 OTA (Klook / GetYourGuide) に 流出。

GAP 03 — 出張型ゆえの スロット 複雑性

時間 × 場所 × 着付師 の 3軸 が Excel では 破綻

ホテル・観光地・自宅など 出張先の 移動時間 を考慮したスロット割り当てが必要。 予約 が 増えるほど ダブルブッキング と 移動 ロス で 現場が疲弊。

GAP 04 — 口コミ資産化

Google / TripAdvisor の 星が、 訪日客の 意思決定 No.1

訪日客 は 現地 の 星 4.7 以上 の レビュー数 で 比較。 施術後 の レビュー誘導 を 多言語 で 自動化 できない と、 満足度が高くても 口コミ資産 が 積み上がらない。

Pillar 03 — 出張スロット 管理 (時間 × エリア × 着付師)

「移動時間 込み」 で スロット を 埋める。 着付師 4名 × 1日 が 現実的キャパ の 最大値 に 到達。

出張型 の 最大 の ボトルネック は 移動時間。 A ホテル → B 神社 → C 民泊 の 順に 回る と 移動 だけで 2時間 消える 日 が 頻発。 このシステムは 予約 が 入った 瞬間 に 前後 の 移動時間 を 自動 バッファ、 現実的 に 詰められる 上限 を 可視化 します。

  • 着付師 ごと の 稼働 カレンダー
  • Google Maps の 実移動時間 を 自動 加算 (兼六園 → 東茶屋街 は 12分 等)
  • ダブルブッキング 物理防止 (予約 admin 側 で 弾く)
  • 着物 在庫 (サイズ・柄) と 連動、 予約時点で 引当
  • キャンセル が 出た 瞬間 空き 復活、 待機客 に 自動 通知
