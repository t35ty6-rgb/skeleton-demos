個人情報 / 金融情報を扱う SaaS の責任ある運用基盤
FPC-SEC-2026-001
2026 年 6 月 5 日
策定: 吉田 恭聡
エグゼクティブ サマリー
FP Compass は個人の年収 / 資産 / 家族構成 / 健康状態等の 要配慮個人情報に準ずる金融情報 を扱う SaaS である。本書では (1) FP がログインする認証方式 (2) FP 顧客の 個人情報を守るセキュリティ対策 (3) 法的責任の整理 を提案する。推奨は Google OAuth + Magic Link バックアップ、データ保管は 各 FP 専用 Google Workspace 内に隔離、規約 / 同意は 業務委託契約 + 個人情報取扱同意書 をセットで締結する。

01 認証方式 — どうやってログインするか

1-1. 4 つの選択肢 比較

方式採点長所短所
Google OAuth推奨パスワード不要 / 漏洩リスク低 / FP の Workspace と相性◎Google アカウント必須 (FP の 70% 以上が利用)
Magic Link (Email)推奨 (補助)パスワード不要 / メールさえあれば誰でも受信遅延 / メールフィルタリング懸念
Email + Password条件付慣れた形式パスワード忘れ / 漏洩 / リセット運用負荷
LINE Login非推奨FP は LINE 習熟業務ツールでの違和感 / Bot 連携と混乱 / 個人 LINE と FP 用が混在しやすい

1-2. 推奨フロー

[FP に招待メール送付] ← Skeleton 営業担当が個別配信 ▼ 招待リンク (有効期限 7 日 / ワンタイム) [Google OAuth ログイン] ▼ OAuth 2.0 / scope: email, profile [テナント作成 (1事務所 = 1テナント)] ▼ 専用 Google Drive folder + 専用 Spreadsheet 自動プロビジョン [専用 CRM URL でログイン状態維持 (Cookie HttpOnly + Secure)] ▼ [再アクセス時は自動ログイン (Refresh Token + 30日)]

1-3. パスワード方式が必要な場合 (補助オプション)

Google アカウント未保有 FP 向けに Magic Link (メール内クリックでログイン、パスワード不要) を補助提供。Magic Link の有効期限は 10 分、使用後は即無効化。

1-4. 多要素認証 (MFA) — Pro プラン以上で必須

金融情報を扱う本質上、Pro プラン以上は MFA 必須。Google Authenticator / Authy / SMS のいずれか。Standard プランは推奨だが任意。

02 セキュリティ — 個人情報をどう守るか

2-1. 多層防御 アーキテクチャ

レイヤー対策実装状態
通信全通信 HTTPS (TLS 1.2 以上) / HSTS済 GitHub Pages / Cloud Run / GAS 全て自動 TLS
認証Google OAuth / Magic Link / MFAPhase 2 実装
認可テナント (fpId) 行レベル分離 + 専用 Sheet 物理分離fpId 済 / 専用 Sheet Phase 2
データ保管各 FP の Google Workspace 内 (Google 側で AES-256 暗号化)済
入力検証XSS 対策 (escapeHtml) / SQL Injection 不存在 (Sheet 直書き)済
API 鍵保管Cloud Run 環境変数 / Google Secret Manager 移行Phase 2 Secret Manager 化
Rate LimitingCloud Run 自動 / Express middleware で API毎制限Phase 2 細粒度化
監査ログ全ログイン / 顧客アクセス / データ削除 を BigQuery 集約Phase 3 実装

2-2. テナント分離 (越境防止)

顧客 A の FP が誤ってでも顧客 B のデータを見れない構造にする。実装:

[FP A ログイン] → fpId = fp001 ↓ アプリ層で fpId を Cookie / Session に保存 [API 呼出] → 全リクエストに自動で fpId 付与 ↓ [GAS / Cloud Run] → 受信した fpId と Cookie の fpId が一致しなければ 403 ↓ [Sheet レイヤー] → fpId カラムでフィルタ (二重チェック) ↓ [Phase 2 以降] → fpId 毎に 専用 Spreadsheet ID + 専用 Drive Folder ID を発行し、アプリは自分のテナントの ID のみアクセス可

2-3. データの場所

顧客台帳
Google Sheets
各 FP の Google Workspace 内 (Phase 2: 専用 Sheet 隔離)
議事録 / 録画
Google Drive
各 FP の専用フォルダ「FP Compass / 顧客名簿」配下
API 鍵 / 秘密情報
Secret Manager
Google Cloud (Phase 2)。コードには含まれない

顧客の個人情報は FP の Google Workspace 内に留まる。Skeleton 側のサーバ (Cloud Run) は処理の経由地であり、データを保存しない。これにより責任分界が明確になる。

2-4. インシデント対応 (漏洩時)

時間アクション
0 〜 1 時間影響範囲特定 / 該当機能即停止 / 監査ログ保全
1 〜 4 時間FP 顧客に第一報 (メール + LINE) / 個人情報保護委員会への報告準備
4 〜 24 時間個人情報保護委員会へ報告 (法律上必須) / 影響を受けたエンドユーザへの通知
24 時間以降原因究明 / 再発防止策策定 / 公式発表 / 補償判断

03 法的責任 — 何を書面で守るか

3-1. 必要な書類 4 点セット

書類用途誰が誰に
① 利用規約サービス提供の条件Skeleton → FP
② プライバシーポリシー個人情報の取扱方針 (公開)Skeleton → 全員
③ 業務委託契約書FP のエンドユーザ情報を Skeleton が処理することの委託Skeleton ⇔ FP
④ 個人情報取扱同意書FP のエンドユーザ向け同意取得テンプレFP → エンドユーザ

3-2. 個人情報保護法 (改正法 / 令和 4 年施行) 対応

重要 5 義務:
① 利用目的の特定・通知 (顧客台帳 / AI議事録の用途を明示)
② 安全管理措置 (本書 2 章の多層防御で対応)
③ 第三者提供制限 (Anthropic / Google への提供は委託扱いとして整理)
④ 開示・訂正・削除請求への対応 (オフボーディング 30日完全削除で対応)
⑤ 漏えい時の報告義務 (本書 2-4 のインシデント対応で対応)

3-3. データ削除権 (Right to be Forgotten)

FP が解約した場合、または FP のエンドユーザが削除を要求した場合、以下のルールで対応:

解約申請D 日FP の管理画面から解約 → データエクスポート (Sheet + Drive zip) を交付
猶予期間D + 30日誤操作 / 再契約のため保持 (再契約時に即復元)
完全削除D + 30日Sheet / Drive / バックアップから完全削除 / 削除証明書発行

06 今すぐ オーナーに 判断してほしい 3 点

① 認証方式: Google OAuth + Magic Link で進めて OK か?
② プラン区分: MFA を Pro プラン以上で必須にして OK か? (Standard は任意)
③ 法的責任: 業務委託契約 + 個人情報取扱同意書 を Phase 1 で締結する方針で OK か?

Yes / No だけ判断いただければ、Jobs 側で Phase 1〜4 を順次実装します。書類のドラフトは Phase 1 で Jobs が起草、最終確認のみオーナーで承認いただきます。
