🔒 サロン別 データ分離 (他社の情報と 絶対に 混ざらない 仕組み)

MULTI-TENANT DATA ISOLATION · ARCHITECTURE PROOF

各サロン は テナントID という 固有 識別子 で 完全 分離。 LINE OA / Token / 予約データ / 顧客カルテ / コース 全部 サロンごと に 別物。

テナントID (tenant ID) = サロンごと に 1つ ずつ 自動 で 振られる 背番号 みたいなもの。 同じ サロン名 が 2つ あっても、 背番号 が 違う から 絶対 混ざらない。サロン名「フェムケアサロン あおい」 → 内部 ID「aoi-salon-x9k4l2」 のように 英数字 で 自動生成
LINE OA = LINE Official Account = LINE公式アカウント の こと。 「@xxxxxx」 で 始まる ID を 持つ ビジネス用 LINE アカウント。 友だち追加 してくれた お客様 に メッセージ を 送れる。フェムケア あおい → @aoi-salon、 B店 → @salonb-cafe、 と サロンごと に 1個 持つ
LINE Token (チャネルアクセストークン) = LINE が 発行する 200文字 くらい の 長い パスワード。 「このトークン を 持ってる 人だけ、 この LINE OA で メッセージ を 送れる」 という 鍵。SaaS が これ を 持ってる から お客様 に「予約承りました」 LINE を 送れる
LIFF ID = LINE内 で 開く Web ページ用 の 設定 ID。 「2010xxxxxx-xxxxxx」 形式。 これ が あると、 LINE から 予約フォーム を 開いた 時 に お客様 の 名前 が 自動 入力 される + 予約完了 LINE が 自動 で 届く。LIFF = LINE Front-end Framework の 略

予約URL.../book/aoi-salon-x9k4l2
LINE OA@aoi-salon
LINE TokenD4K2eF7g...(専用)
LIFF ID2010xxxxxx-aoi

LINE OA@salonc-relax
LINE TokenQ8h2lL5...(専用)

3重の 分離保証

  • ① テナントID で完全分離 — Firestore は tenants/{salonId}/bookings 構造。 サロン あおい さん の 予約 は tenants/aoi-salon-x9k4l2/bookings/... にしか入らない
  • ② Firestore Rules で アクセス遮断 — サロンA の ログインユーザー は サロンB の データ を 読めない (rules で auth.uid から tenantId を 引いて 一致確認)
  • ③ LINE OA も 完全別アカウント — サロン あおい の 予約通知 は @aoi-salon から だけ 飛ぶ。 サロン B の お客様 に 届く 可能性 ゼロ
Firestore Rules (セキュリティルール) = データベース の 入り口 の 警備員。 「あなた は サロン A の 人だから サロン A の データ しか 見せない」 と 1件ずつ チェック して 弾く 仕組み。 コード で 設定 した ルール は 全リクエスト に 強制適用 されて バイパス 不可。マンション の オートロック みたいに 鍵 が 合わない 部屋 は 開かない
auth.uid = 認証 (auth) されてる ユーザー の 固有ID。 ログイン した 時 に Firebase が 発行 する 番号。 これ を 使って 「このログイン中 の ユーザー が どのサロン に 属してるか」 を 1件1件 確認 する。入館証 の 顔写真 と 入る部屋 を 照合 する イメージ

⚠️ もし エラー が 起きたら? (オーナー が 動く 必要 が ある 場面)

FAILURE MODES · RECOVERY · WHEN OWNER NEEDS TO ACT
😱 申込書 が 不完全 で 送信失敗 (例: メアド の 形式ミス)
サロン側 で フォームバリデーション エラー が 出る → サロン担当者 が 修正 して 再送信。 オーナー対応 不要。
😱 LINE OA 作成 で 詰まった (LINE側 の 一時障害 等)
Jobs が エラー検知 → オーナー LINE に「⚠️ ○○サロン さん LINE側 エラー、 リトライします」 と 自動通知。 30分後 に Jobs が 再試行。 3回失敗したら Jobs が「手動 セットアップ 要」 と オーナー に エスカレーション。
😱 完成通知メール が サロン に 届かない (迷惑メール 振り分け 等)
Jobs が 24時間以内 に ログイン が 無いことを 検知 → オーナー LINE に「○○サロン さん 未ログイン、 担当者に 別経路 で 連絡推奨」。 オーナー が サロン に 「メール届いてる?」 と 確認。
😱 サロン から 「使い方 分からない」 と 質問 が 来た
サロンが 直接 オーナー に LINE → オーナー は Jobs に 1行 転送: 「あおい サロン さん が 予約削除の方法 が 分からない と」 → Jobs が 即 回答案 を 作って オーナー に 返信 (オーナー が サロンに 転送)
😱 サロン が 月額¥3,000 を 振込忘れ
Jobs が 月末 に 未入金 検知 → オーナー LINE に「○○サロン 未入金」 通知。 オーナー が サロン に リマインダー 送付。 (Phase E で Stripe 自動引き落とし にすると これも自動化)

📚 用語集 (これ 見れば 全部 分かる)

GLOSSARY · TECHNICAL TERMS EXPLAINED FOR EVERYONE

サロン担当者 / 営業先 で 「これ 何?」 と 聞かれそう な 用語 を 全部 やさしく 解説。 1枚 で 全員 が 理解 できる レベル に まとめた。

SaaS ビジネス
月額 で 使う ネット上 の ツール
Software as a Service の 略。 自分の PC に 入れず、 ブラウザ で 開いて 使う。 アップデート は 自動、 メンテ も 全部 提供側。 利用料 を 月額 で 払う。
FEMOON SaaS = サロン が 月¥3,000 で 使える 予約管理 サービス
API 技術
プログラム同士の 会話の窓口
Application Programming Interface の 略。 「ここから 情報 を 受け渡す よ」 という 決まった 窓口。 LINE が 公開してる API を 使う と 「メッセージ送って」 を プログラム から お願い できる。
SaaS → LINE API で 「予約承りました」 メッセージ を お客様 に 送ってる
Messaging API LINE
LINE で メッセージ を 自動 で 送る 仕組み
LINE が 用意してる API の 1つ。 これ を 使う と 「特定 の お客様 に この メッセージ 送って」 と プログラム から お願い できる。 一斉配信 や 個別配信 も 可能。
予約完了 LINE / 一斉配信 LINE は 全部 Messaging API 経由
Webhook 技術
「○○が起きたら 教えて」 自動通知
「サロン の LINE で 友だち追加 が あった時 / メッセージ来た時 に 自動で URL を 叩く」 仕組み。 「お知らせ用 の 玄関ベル」 みたいなもの。 これ で SaaS が LINE の 動き を リアルタイム検知 できる。
例: お客様 が LINE で 公式アカウント に 「○月○日 空いてる?」 と 送る → Webhook で SaaS に 通知 → 自動返信 で 予約フォーム URL を 送り返す
Phase E で 自動応答 つける時 に 使う 予定 (今は 基本機能 で 未使用)
トークン (Token) 技術
200文字 くらい の 「合言葉」
長い ランダム な 文字列 で、 「これ を 持ってる 人だけ 操作 OK」 という 鍵 の 役割。 LINE Messaging API は この トークン を 確認 して、 認可 された ユーザー だけ メッセージ を 送れる。
サロンごと に 違う トークン → 他サロン の LINE では メッセージ送れない
LINE OA (公式アカウント) LINE
@xxxxxx で 始まる ビジネス用 LINE
LINE Official Account = LINE公式アカウント の 略。 サロン / 店舗 / 企業 が 使う ビジネス用 LINE アカウント。 一般 ユーザー の LINE と 違って 「友だち追加」 してくれた 人 に 一斉配信 できる。
サロン あおい → @aoi-salon、 サロンB → @salonb-cafe、 と サロンごと に 別アカウント
LIFF LINE
LINE内 で 開く Web ページ用 SDK
LINE Front-end Framework の 略。 「LINE アプリ の 中 で 開く Web ページ」 用 の 設定。 これ を 使う と LINE 内 で 開いた お客様 の 名前 や userId が 自動 取得 できる。
結果: お客様 は 名前 を 入力 する 必要 が 無い + 予約完了 LINE が 自動 で 届く
予約フォーム を LINE 内 で 開いた 時 だけ LIFF SDK が 動く (Web で 開く と 動かない)
テナント (tenant) 技術
マンション の 1部屋 のようなもの
同じ システム を 複数 の 顧客 (この場合 サロン) で 共有 使用 する時、 各顧客 の 領域 を 「テナント」 と 呼ぶ。 マンション の 1部屋 と 同じ。 部屋 の カギ (tenantID) で 区切られて 隣 の 部屋 と 完全 別物。
FEMOON SaaS = 100サロン 入る マンション。 各サロン = 1部屋 = 1テナント
Firestore 技術
Google の クラウド データベース
Google が 提供 する NoSQL データベース。 「Excelシート の 巨大版」 と 思えば OK。 大量 の データ を 整理して 保存 + リアルタイム同期 + セキュリティルール で アクセス制御 が できる。
SaaS の 全データ (予約 / 顧客 / コース / 設定) が ここ に 入ってる
Firebase 技術
Google の Webアプリ 部品セット
Firestore + Auth (認証) + Hosting (公開) を 全部 含む Google の 「Webアプリ部品セット」。 SaaS が これ で 動いてる。 Spark プラン (= 無料) なので 当面 コスト ¥0。
https://skeleton-femoon-saas.web.app/ は Firebase Hosting で 公開
認証 (Auth / Authentication) 技術
「あなた が 誰か」 を 確認 する仕組み
ログイン の こと。 メアド + パスワード で 「この人 は サロン A の 担当者」 と Firebase が 確認 する。 ログイン後 は 自動で セッション保持 (= 毎回 ログイン しなくて 良い)。
サロン担当者 が SaaS に ログイン する時 に Firebase Auth が 認証
セキュリティルール (Rules) 技術
データベース の 警備員
「あなた は サロン A の 人 だから サロン A の データ しか 見せない」 と 1件1件 チェック して 弾く 仕組み。 コード で 書いた ルール が 全リクエスト に 強制適用 されて 抜け道 無し。
サロンA の ログインユーザー → サロンB の 予約データ にアクセス → Rules が 即座に 拒否
Playwright 技術
ブラウザ を 自動操作 する ロボット
人間 が ブラウザで やる 操作 (クリック / 入力 / スクショ) を プログラム で 自動 化 する Microsoft の ツール。 これ で Jobs が LINE管理画面 を 自動操作 して セットアップ する。
Jobs が サロン専用 LINE OA を 作る 時 に これ で 全自動 操作
Cron / cron job 技術
時間 で 自動実行 する スケジューラ
「毎朝 7時 に これ を 実行 して」 と 時間指定 で プログラム を 動かす 仕組み。 サーバ の 中 で 静かに 24時間 待機 → 指定時間 で 起動。
Jobs が 毎朝 ヘルスチェック / 月末 に 未入金 検知 する 時 に 使う
Stripe ビジネス
クレカ決済 の 仕組み
アメリカ の 決済代行 サービス。 月額課金 / クレカ自動引き落とし を 簡単 に 組める。 Phase E で SaaS に 組むと サロン から の 入金 が 完全自動 化 される。
未統合 (Phase E で 月¥3,000 自動引き落とし化 予定)
マルチテナント (multi-tenant) 技術
1つ の システム を 複数顧客 で 共有
FEMOON SaaS が まさに これ。 サーバ 1つ で 100サロン 動かせる。 ただし 各サロン の データ は 完全分離 (テナントID で 区切り)。 経済的 + 保守も楽。
100サロン 増えても サーバ 増設 不要、 月¥0 で 拡張可能
HTTPS 技術
通信を 暗号化 する 仕組み
「https://」 で 始まる URL は 通信内容 が 暗号化 されて 第三者 に 盗聴 されない。 個人情報 / パスワード / クレカ番号 を 送る時 に 必須。
SaaS の 全URL が HTTPS。 サロン と お客様 の 通信 が 暗号化 されて 安全
Hosting (ホスティング) 技術
Web ページ を 公開する 置き場所
Web ページ を インターネット に 公開 する サーバ。 「ホスティング サービス」 が 24時間 動かしてくれる。 Firebase Hosting と GitHub Pages を 使ってる。
SaaS本体 = Firebase Hosting / 申込書 や ガイド = GitHub Pages
ストック収入 ビジネス
毎月 自動 で 入る 売上
「フロー収入 (1回限り の 売上)」 の 逆。 月額契約 の SaaS は 1サロン 受注 すれば 解約 されるまで 毎月 売上 が 入る。 これ が SaaS ビジネス の 最強 ポイント。
10サロン × ¥3,000/月 = 月¥30,000 が 毎月 自動 で 入る (1回 営業 すれば 永久)
SLA / アップタイム ビジネス
「99.9%動きます」 の 保証
Service Level Agreement の 略。 「年間 で 99.9% の 時間 は サービス が 動いてます」 と いう 稼働率保証。 Firebase は 99.95% 保証。 サロン に「年間 8時間 程度 メンテで 止まります」 と 告知 推奨。
Firebase 99.95% = 1年で 約4時間 のメンテ枠。 ほぼ 24時間 動く
