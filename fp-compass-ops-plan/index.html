策定: 吉田 恭聡
エグゼクティブ サマリー
本書は FP Compass を 100 社規模で運用 しながら、開発を継続的に進める ための運用基盤の設計提案である。現状の 1 環境 + 1 デプロイ構成では、1 社向けの修正が全社に瞬時に波及し、不具合発生時のリスクが累積的に増大する。本提案では 環境分離 / 自動テスト / 段階展開 / 監視 / 顧客管理基盤 の 5 領域 を 4 フェーズに分けて段階構築し、売上拡大と品質保証を両立する。実装期間は Phase 1〜4 で 6〜9 ヶ月、初期投資 120〜180 万円相当 (Jobs内製) と試算する。

01 現状リスクと基本方針

現在は 1 つの本番 URL を全顧客が共有する単一環境構成。顧客データは fpId による行レベル分離が実装済だが、アプリケーションコードは全顧客共通 のため、特定顧客向けの修正・実験的機能・プロンプト変更が他顧客に予期せぬ影響を与えるリスクがある。

優先主要リスク顧客から見える症状
必須破壊的デプロイ全社が同時にエラー / 機能停止 / 顧客対応中に画面崩れ
必須プロンプト変更による品質劣化AI 議事録 / 下書きの精度が突如低下 / 出力フォーマット崩れ
必須障害の検知遅延顧客が「使えない」と通報するまで Jobs が気付けない
推奨単一顧客の負荷スパイク1 社の大量処理が他社のレスポンスを劣化させる
推奨設定変更のヒューマンエラー環境変数・シークレット誤更新で全社停止
将来データ漏洩 / 越境fpId フィルタの実装漏れで他社データが見える
基本方針: 「変更による影響を本番に届くまでに 3 段階でフィルタする」「機能フラグで顧客毎にロールアウトを制御する」「全イベントを監視し、24 時間以内に検知する」。

02 4 環境分離 × 段階デプロイ

開発から本番までを 4 つの環境に分離。コード変更は必ず Local → Preview → Staging → Production の 4 段階を経由する。Production への適用は週 1〜2 回まとめて行い、緊急修正以外は不定期デプロイを禁止する。

[Local 開発] Jobs 環境 / hot reload / 自由に試行錯誤 ▼ PR 作成 (GitHub) [Preview] PR 毎にユニーク URL 自動発行 (Cloudflare Pages preview) ▼ オーナー or レビュアーが手元で動作確認 [Staging] fp-crm-stg/ 常設 / 1 ダミー顧客で 24〜48h 実地検証 ▼ E2E テスト 全件 PASS + ステークホルダー承認 [Production] fp-crm/ 100 社が利用 / 週次 or 隔週リリース

段階ロールアウト戦略 (Feature Flag)

新機能は 機能フラグ で顧客毎に ON/OFF 制御。Production に適用後も、最初は Jobs 内部 → パイロット 3 社 → ベータ 10 社 → 一般展開 (GA) の順で段階開放する。想定外の挙動が発生した時点で、ロールバックではなく フラグを切るだけで全顧客から無効化 できる。

Blue / Green デプロイ (Cloud Run)

バックエンドの Cloud Run は新 revision を deploy 後、最初は traffic 5% にのみ振り分け、5〜30 分のモニタリングでエラー率に異常が無いことを確認してから 100% に切替。問題発生時は 30 秒で旧 revision に traffic を戻す。

05 顧客管理基盤 (Tenant Admin)

5-1. 認証 / アカウント

Google OAuth (FP 業界は Google Workspace 普及率 70% 超) でログイン。1 事務所 = 1 テナント。複数ユーザ (所長 / アシスタント) 登録可、ロールは Owner / Admin / Staff の 3 段階。

5-2. データ隔離 (テナンシ)

既存実装の fpId 行レベル分離を強化し、テナントごとに専用 Google Drive フォルダ + 専用 Spreadsheet を自動プロビジョニング。アプリケーションコードからは「自分のテナントの Sheet ID」のみアクセス可能とし、相互参照を物理的に不可とする。

06 4 フェーズ ロードマップ

  1. 基盤整備 (現状 〜 5 社)
    期間: 1 ヶ月 / 工数: 約 30h / 投資: 15 万円相当
    ① 3 環境分離 (Preview / Staging / Production)
    ② Playwright スモークテスト 15 件構築
    ③ GitHub Actions による CI/CD 基本パイプライン
    ④ ロールバック手順書 整備 (PDF 化 + 印刷 + 屋内掲示)
    ⑤ UptimeRobot による外形監視 (5 分間隔)
  2. 顧客管理基盤 (5 社 → 20 社)
    期間: 2 ヶ月 / 工数: 約 80h / 投資: 40 万円相当
    ① Google OAuth ログイン + テナント設計
    ② Stripe Subscription 連携 (4 プラン)
    ③ オーナー側 管理ダッシュボード (全顧客一覧 / 利用統計 / 機能フラグ)
    ④ オンボーディング自動化 (Drive / Sheet プロビジョニング Script)
    ⑤ ステータスページ 公開
  3. 品質保証 強化 (20 社 → 50 社)
    期間: 2 ヶ月 / 工数: 約 60h / 投資: 30 万円相当
    ① Blue / Green デプロイ (Cloud Run traffic splitting)
    ② Sentry によるフロント例外 自動収集
    ③ AI 出力 レグレッション テスト (サンプル議事録 10 件)
    ④ 機能フラグ 完全実装 (顧客毎 / ロール毎 / 段階開放)
    ⑤ サポートチケットシステム (LINE / Slack 統合)
  4. スケール対応 (50 社 → 100 社)
    期間: 3 ヶ月 / 工数: 約 100h / 投資: 50 万円相当
    ① CS (カスタマーサクセス) 担当 1 名採用 / 教育
    ② 月次定例レポート 自動生成 (各顧客の利用統計を PDF 自動配信)
    ③ SRE 自動化 (障害時の自動 Rollback / 自動 Re-Provisioning)
    ④ プラン別 機能差別化 (Enterprise 専用機能の独立コードパス)
    ⑤ アカウント拡張 (代理店プログラム / 紹介報酬制度)
