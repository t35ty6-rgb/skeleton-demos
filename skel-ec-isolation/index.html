SAFETY GUARANTEES

引き継ぎは 確実 か?
サロンの情報は 絶対に混ざらない か?

このドキュメントは、 オーナー (吉田) と Jobs (Cloud Functions) の間で 引き継ぎが エラーなく動くか、 サロンA の情報が サロンB に絶対漏れないか、 を技術的に保証する仕組みを説明します。

心配 1: サロンA と サロンB のデータが 混ざらないか?

⚠
たとえば: 「IDEAL by Hikaru」 サロンの顧客が、 「○○整骨院」 のオーナー画面に出てきてしまったら 信用問題。 LINE の自動応答も、 IDEAL の話を 整骨院に返したら大問題。 これは絶対に起きないか?
✓
答え: 絶対に起きません。 4層のテナント分離で物理的に防いでます。 以下の仕組みで保証されてます。

📁 Firestore のデータ構造

各サロンのデータは、 サロン名 (tenantId) で完全に分かれた "フォルダ" に保存されてます:

📂 /tenants/
  📂 hikari-salon/  ← IDEAL by Hikaru サロンの全データ
    📂 products/ (商品)
    📂 orders/ (注文)
    📂 customers/ (顧客 = LINE友だち)
    📂 messages/ (配信)
    📂 coupons/
    📄 line (LINE Channel ID/secret/access_token)
    📄 stripe (Stripe API キー)

  📂 momoi-salon/  ← ○○整骨院 の全データ (完全に別フォルダ)
    📂 products/
    📂 orders/
    📂 customers/
    ...

  📂 third-salon/  ← サロン3軒目
    ...

物理的に別フォルダなので、 hikari-salon の処理コードが momoi-salon のデータに 触れることが そもそも不可能。 Cloud Function は毎回 「どのサロンの依頼か」 を URL/イベントから判別してから、 そのサロンのフォルダだけ操作します。

🔐 アクセス分離の 4層

層 1

🌐URL レベル

Webhook URL に /サロン名/ が必ず付く
例: /lineWebhook/hikari-salon

層 2

🔑署名検証

LINE からの通信はそのサロン専用の channel_secretで署名検証。 別サロンの token では検証 NG

層 3

🏷メタデータ

Stripe イベントには必ず metadata.tenantId 付与。 ない決済は無視される

層 4

🛡Firestore Rules

admin ユーザーは 自分が所属する tenantId のフォルダしか読めない (DB側で強制)

具体例: サロンA と サロンB

🌸 IDEAL by Hikaru

tenantId: hikari-salon Webhook: /lineWebhook/hikari-salon channel_id: 2010111111 access_token: aBcDe...
顧客 48 名 / 注文 12 件 / 商品 23 点
↑ 全部 hikari-salon フォルダだけ
独立

🏥 ○○整骨院

tenantId: momoi-salon Webhook: /lineWebhook/momoi-salon channel_id: 2010222222 access_token: xYzAb...
顧客 120 名 / 注文 34 件 / 商品 8 点
↑ 全部 momoi-salon フォルダだけ

混ざる可能性ゼロの理由: Cloud Function が 友だち追加 イベントを受け取った時、 URL の末尾 (/hikari-salon or /momoi-salon) を見て「どっちのサロンか」 を判別。 それに対応する Firestore フォルダだけ書き込みます。 さらに LINE 署名検証で「本物の hikari-salon からの依頼か」を二重確認。

心配 2: 引き継ぎ中に失敗したら? 中途半端な状態にならないか?

⚠
たとえば: 「自動セットアップ」 ボタン押したけど、 LINE Webhook 登録は成功して Stripe Webhook 作成は失敗、 みたいな中途半端な状態になったら、 サロンに「動きません」 って怒られる。 どう防いでる?
✓
答え: 各ステップごとに 成功/失敗を個別に記録 + 失敗ステップだけ再実行可能 + すべてべき等 (何度押しても同じ結果) な設計。

自動セットアップの 6 ステップ (チェックポイント方式)

  • ① LINE webhook URL を LINE 側に登録
    PUT /v2/bot/channel/webhook/endpoint 成功 → 緑チェック
  • ② LINE Use webhook を ON
    PUT /v2/bot/channel/webhook/setting 成功 → 緑チェック
  • ③ LINE → 自社サーバー 疎通テスト
    POST /v2/bot/channel/webhook/test success: true → 緑チェック
  • ④ Stripe webhook endpoint 作成 ← 仮に失敗したケース
    例: Stripe sk のスペル間違い → エラー詳細を画面に表示
    ⚠️
    対処: モーダルに「Stripe sk を確認してください」と理由表示 → オーナーが Stripe sk を修正して再度 「自動セットアップ」 ボタン押す → ① ② ③ は スキップ (既に成功してるので) → ④ から再実行 → 成功すれば緑チェック
  • ⑤ Stripe webhook secret を保存
    ④ が成功してから自動実行
  • ⑥ Firestore tenant doc 作成
    最後に書き込み (merge=true なので何度書いても安全)

もし全部失敗しても データは無傷

セットアップが全部失敗しても、 Firestore に書き込む前に止まる ので、 サロンのデータが壊れることはありません。 元の状態のまま 何度でもやり直せます。

🔄
「べき等」 設計: 同じセットアップを 何度実行しても結果は同じ。 既に登録済みなら 「既に設定済」 と判定してスキップ、 失敗した箇所だけ再試行。

心配 3: Jobs (Cloud Functions) は そのサロン専用で 動いてくれるか?

⚠
たとえば: サロンA の友だち追加イベントを Jobs が受け取った時、 ちゃんと サロンA の設定で welcome メッセージ送ってくれるか? サロンB の welcome 文を間違って送ったりしないか?
✓
答え: イベントを受け取るたびに URL から tenantId を抽出 → そのサロンの設定を Firestore から読む → そのサロンのトークンで応答 という流れ。 別サロンの設定を読むコード自体がありません。

Cloud Function のコード抜粋 (友だち追加処理)

exports.lineWebhook = onRequest(async (req, res) => {
  // 1) URL から tenantId を抽出 (例: /lineWebhook/hikari-salon → 'hikari-salon')
  const tenantId = req.params.tenantId;

  // 2) そのサロン専用の設定を Firestore から読み込む
  const tenant = await db.collection('tenants').doc(tenantId).get();
  const cfg = {
    channelSecret: tenant.line.channel_secret, // ← このサロン専用
    channelAccessToken: tenant.line.access_token // ← このサロン専用
  };

  // 3) LINE 署名を このサロンの secret で検証
  if (!validateSignature(req.rawBody, cfg.channelSecret, signature)) {
    return res.status(401).send('別サロンからの依頼かも → 拒否');
  }

  // 4) このサロンのフォルダにだけ書き込む
  await db.collection('tenants').doc(tenantId) // ← 必ず tenantId 経由
    .collection('customers').doc(lineUserId).set({...});
});

注目ポイント: 4 箇所すべてで tenantId 変数を使う設計。 別のサロンのデータに触る方法が そもそもコードに存在しない。

心配 4: オーナーから Jobs への引き継ぎは スムーズか?

⚠
たとえば: オーナーが credentials を貼り間違えた、 サロン slug を間違えた、 みたいな 人為的ミス を Jobs はちゃんと検知してくれるか?
✓
答え: Jobs は credentials を受け取った瞬間に 5項目バリデーション + 本番セットアップ前に LINE/Stripe に試し問い合わせ。 ミスがあれば 何も保存せず エラー報告。

受け取った瞬間にする確認

  • サロン slug 形式チェック
    英小文字/数字/ハイフン 2〜40字以内か? 全角混入? 空白混入? → NG なら即返却
  • Channel ID 形式チェック
    10桁数字か? 改行混入? → NG なら即返却
  • access_token 有効性チェック
    LINE API GET /v2/bot/info に問い合わせ → 200 OK 返ってこなければ token 無効 / 期限切れ と判定 → 保存せずエラー報告
  • Stripe sk 有効性チェック
    Stripe API accounts.retrieve に問い合わせ → エラー返れば sk 無効と判定
  • 同じ slug の tenant が既に存在しないか確認
    他のサロンと slug 衝突したら、 サロン名変更を促す

全部 OK の時だけ、 ようやく Firestore tenant doc 作成 + LINE/Stripe 設定の自動登録 に進みます。 バリデーション失敗時は 何も保存せず、 何を直すべきか具体的に オーナーに返却。

🛡️

このシステムは安心して 複数サロンに販売できます

Firestore のテナント分離、 LINE 署名検証、 Stripe メタデータ強制、 Firestore ルール、 4層の物理分離で データの混ざりは 絶対起きません。 セットアップエラーは個別に検知 + べき等で何度でもやり直し可能。 同じ仕組みで FP Compass が半年無事故稼働中 の実績あり。
