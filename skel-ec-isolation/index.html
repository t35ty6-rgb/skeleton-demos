SAFETY GUARANTEES

引き継ぎは 確実 か?
サロンの情報は 絶対に混ざらない か?

このドキュメントは、 オーナー (吉田) と Jobs (Cloud Functions) の間で 引き継ぎが エラーなく動くか、 サロンA の情報が サロンB に絶対漏れないか、 を技術的に保証する仕組みを説明します。

読み方ガイドこのページの オレンジ色の点線下線 は 専門用語。 マウスを乗せる/タップ すると 3秒で分かる解説 がポップアップ。 セクションごとに 💡黄色 / ❓青 / 🌱緑 の吹き出しで補足。 「全部読み込まなくても 用語だけ拾えば全体像が掴める」 設計にしてあります。

= 通知が来た時だけ起動する 受付プログラム。 普段は休んでて、 必要時だけ動くので 月額ほぼ¥0。

心配 1: サロンA と サロンB のデータが 混ざらないか?

⚠
たとえば: 「IDEAL by Hikaru」 サロンの顧客が、 「○○整骨院」 のオーナー画面に出てきてしまったら 信用問題。 LINE の自動応答も、 IDEAL の話を 整骨院に返したら大問題。 これは絶対に起きないか?
✓
答え: 絶対に起きません。 4層のテナント分離で物理的に防いでます。 以下の仕組みで保証されてます。
用語「テナント (tenant)」 って何?
テナント = 1サロン分の専用エリア。 ビルで言うと「101号室」「102号室」。 同じビルに住んでても部屋は完全に別。 Skel·EC では 1サロン = 1テナント。 サロンA は hikari-salon、 サロンB は momoi-salon という名札 (これを tenantId と呼ぶ)。

📁 FirestoreFirestore = Google が提供する クラウドデータベース。 商品/顧客/注文 など 全データの 保存先。 大手SaaS (LINE 公式アカウント Manager 等) も同系統を使用。 のデータ構造

各サロンのデータは、 サロン名 (tenantIdtenantId = サロンを識別する短い名前 (英小文字+数字+ハイフン)。 例: hikari-salon。 URL や データ保存先 すべてに使われる "サロン名札"。) で完全に分かれた "フォルダ" に保存されてます:

📂 /tenants/
  📂 hikari-salon/  ← IDEAL by Hikaru サロンの全データ
    📂 products/ (商品)
    📂 orders/ (注文)
    📂 customers/ (顧客 = LINE友だち)
    📂 messages/ (配信)
    📂 coupons/
    📄 line (LINE Channel ID/secret/access_token)
    📄 stripe (Stripe API キー)

  📂 momoi-salon/  ← ○○整骨院 の全データ (完全に別フォルダ)
    📂 products/
    📂 orders/
    📂 customers/
    ...

  📂 third-salon/  ← サロン3軒目
    ...

物理的に別フォルダなので、 hikari-salon の処理コードが momoi-salon のデータに 触れることが そもそも不可能。 Cloud FunctionCloud Function = サロンから「友だち追加されたよ」「商品が買われたよ」 という通知が来た時に、 一瞬だけ起動して処理する "受付プログラム"。 普段は休んでて、 必要な時だけ動くから 月¥0〜数百円で済む。 は毎回 「どのサロンの依頼か」 を URL/イベントから判別してから、 そのサロンのフォルダだけ操作します。

🏠 ホテル の場合

101号室 のお客様が頼んだルームサービスは 必ず 101号室に 届く。 102号室には絶対届かない。 ホテル名: 部屋番号 で識別してるから。

💻 Skel·EC の場合

サロンA に送られた LINE 友だち追加 は 必ず サロンA の顧客リスト に追加される。 サロンB には絶対追加されない。 名札: tenantId で識別してるから。

🔐 アクセス分離の 4層

補足「4層」 って何?
1個の壁で守るんじゃなくて、 4枚の壁 を重ねて守る設計。 1枚突破されても 残り3枚で止まる。 銀行の金庫が 「ドア → ガラス → センサー → 警報」 と多重防御してるのと同じ。 1枚抜けただけで全滅 にならない。
層 1

🌐URL レベル

WebhookWebhook = サーバー同士の「呼び鈴」。 LINE で誰かが友だち追加すると、 LINE が Skel·EC に「ピンポーン、追加されたよ」 と自動で通知する 専用URL。 URL に /サロン名/ が必ず付く
例: /lineWebhook/hikari-salon

層 2

🔑署名検証署名検証 = 「これ本物?」 の確認。 LINE は秘密のハンコ (channel_secret) で 通知に印鑑を押す。 Skel·EC 側で同じハンコで照合。 偽通知は弾く。

LINE からの通信はそのサロン専用の channel_secretchannel_secret = LINE が発行する 各サロン専用の "ハンコの形"。 これでハンコが押されてる 通知 だけ 本物と認める。 サロンごとに別々で、 オーナーが LINE Console から取得して Skel·EC に登録する。で署名検証。 別サロンの token では検証 NG

層 3

🏷メタデータメタデータ (metadata) = 決済に付ける "タグ"。 Stripe で 決済が走るたびに「これは hikari-salon の決済」 という ラベル を必ず貼る。 ラベルなしの決済は 偽物として無視。

Stripe イベントには必ず metadata.tenantId 付与。 ない決済は無視される

層 4

🛡Firestore RulesFirestore Rules = データベース側の "通行証チェック"。 「あなたは hikari-salon のオーナー? じゃあ hikari-salon のフォルダしか読み書きできません」 と DB自体が拒否。 アプリのバグでうっかり別フォルダに触っても DB が止める。

admin ユーザーは 自分が所属する tenantId のフォルダしか読めない (DB側で強制)

混ざる可能性ゼロの理由: Cloud Function が 友だち追加 イベントを受け取った時、 URL の末尾 (/hikari-salon or /momoi-salon) を見て「どっちのサロンか」 を判別。 それに対応する Firestore フォルダだけ書き込みます。 さらに LINE 署名検証で「本物の hikari-salon からの依頼か」を二重確認。

心配 2: 引き継ぎ中に失敗したら? 中途半端な状態にならないか?

⚠
たとえば: 「自動セットアップ」 ボタン押したけど、 LINE Webhook 登録は成功して Stripe Webhook 作成は失敗、 みたいな中途半端な状態になったら、 サロンに「動きません」 って怒られる。 どう防いでる?
✓
答え: 各ステップごとに 成功/失敗を個別に記録 + 失敗ステップだけ再実行可能 + すべてべき等 (何度押しても同じ結果) な設計。
用語「べき等 (idempotent)」 って何?
難しい言葉だけど、 意味はシンプル: 何度ボタンを押しても 結果が変わらない こと。 エレベーターのボタンを 5回連打しても 1回しか来ない (= べき等)。 セットアップを 5回押しても 設定が 5倍積み重なる事はなく、 必ず "正しい1回分の状態" になる。 連打しても壊れない安心設計。

自動セットアップの 6 ステップ (チェックポイント方式)

補足「チェックポイント方式」 = ゲームのセーブポイントと同じ。 ④で失敗しても、 ①②③ の セーブデータは残ってるから、 そこから再開できる。 最初からやり直さなくていい。
  • ① LINE webhook URL を LINE 側に登録
    PUT /v2/bot/channel/webhook/endpoint 成功 → 緑チェック
  • ② LINE Use webhook を ON
    PUT /v2/bot/channel/webhook/setting 成功 → 緑チェック
  • ③ LINE → 自社サーバー 疎通テスト
    POST /v2/bot/channel/webhook/test success: true → 緑チェック
  • ④ Stripe webhook endpoint 作成 ← 仮に失敗したケース
    例: Stripe sk のスペル間違い → エラー詳細を画面に表示
    ⚠️
    対処: モーダルに「Stripe sk を確認してください」と理由表示 → オーナーが Stripe sk を修正して再度 「自動セットアップ」 ボタン押す → ① ② ③ は スキップ (既に成功してるので) → ④ から再実行 → 成功すれば緑チェック
  • ⑤ Stripe webhook secret を保存
    ④ が成功してから自動実行
  • ⑥ Firestore tenant doc 作成
    最後に書き込み (merge=true なので何度書いても安全)

もし全部失敗しても データは無傷

セットアップが全部失敗しても、 Firestore に書き込む前に止まる ので、 サロンのデータが壊れることはありません。 元の状態のまま 何度でもやり直せます。

🔄
「べき等」 設計: 同じセットアップを 何度実行しても結果は同じ。 既に登録済みなら 「既に設定済」 と判定してスキップ、 失敗した箇所だけ再試行。

心配 3: Jobs (Cloud Functions) は そのサロン専用で 動いてくれるか?

⚠
たとえば: サロンA の友だち追加イベントを Jobs が受け取った時、 ちゃんと サロンA の設定で welcome メッセージ送ってくれるか? サロンB の welcome 文を間違って送ったりしないか?
✓
答え: イベントを受け取るたびに URL から tenantId を抽出 → そのサロンの設定を Firestore から読む → そのサロンのトークンで応答 という流れ。 別サロンの設定を読むコード自体がありません。
考え方「URL から判別」 = 郵便配達と同じ
郵便配達員は 宛名 (住所) を見てから その家のポストに入れる。 配達員が勝手に隣の家に入れる事はない。 Skel·EC も同じ: 通知が来たら まず URL の宛名 (/lineWebhook/hikari-salon) を見てから、 hikari-salon フォルダにだけ書き込む。

Cloud Function のコード抜粋 (友だち追加処理)

補足「コード」 が読めなくても OK。 大事なのは下のコード内に tenantId という言葉が 4回出てくる事。 それぞれが「どのサロンか」 を毎回チェックしてる証拠。 別のサロンに触る道がコードに無い、 ということを目で確認するための表示。
exports.lineWebhook = onRequest(async (req, res) => {
  // 1) URL から tenantId を抽出 (例: /lineWebhook/hikari-salon → 'hikari-salon')
  const tenantId = req.params.tenantId;

  // 2) そのサロン専用の設定を Firestore から読み込む
  const tenant = await db.collection('tenants').doc(tenantId).get();
  const cfg = {
    channelSecret: tenant.line.channel_secret, // ← このサロン専用
    channelAccessToken: tenant.line.access_token // ← このサロン専用
  };

  // 3) LINE 署名を このサロンの secret で検証
  if (!validateSignature(req.rawBody, cfg.channelSecret, signature)) {
    return res.status(401).send('別サロンからの依頼かも → 拒否');
  }

  // 4) このサロンのフォルダにだけ書き込む
  await db.collection('tenants').doc(tenantId) // ← 必ず tenantId 経由
    .collection('customers').doc(lineUserId).set({...});
});

注目ポイント: 4 箇所すべてで tenantId 変数を使う設計。 別のサロンのデータに触る方法が そもそもコードに存在しない。

心配 4: オーナーから Jobs への引き継ぎは スムーズか?

⚠
たとえば: オーナーが credentials を貼り間違えた、 サロン slug を間違えた、 みたいな 人為的ミス を Jobs はちゃんと検知してくれるか?
✓
答え: Jobs は credentials を受け取った瞬間に 5項目バリデーション + 本番セットアップ前に LINE/Stripe に試し問い合わせ。 ミスがあれば 何も保存せず エラー報告。
用語「credentialscredentials = 「認証情報」 のかたまり。 LINE の channel ID/secret/access_token、 Stripe の sk_live_xxxxx 等、 サロンを特定する 鍵束。 オーナーが LINE Console / Stripe Dashboard から取得して Jobs に渡す。」 = 鍵束。 LINE Channel の3点セット (ID / secret / access token) + Stripe sk。 これがないと LINE/Stripe を サロン専用で動かせない。
補足「slugslug (スラッグ) = URL に使える短い識別子。 英小文字+数字+ハイフンのみ。 サロン名「IDEAL by Hikaru」 → slug「hikari-salon」 みたいに 変換して使う。 tenantId と同義。」 = URL に使える "短い名札"。 「IDEAL by Hikaru」 → hikari-salon の様に変換。 これを間違えると 違うサロンの URL に登録されちゃうから厳密にチェック。

受け取った瞬間にする確認

  • サロン slug 形式チェック
    英小文字/数字/ハイフン 2〜40字以内か? 全角混入? 空白混入? → NG なら即返却
  • Channel ID 形式チェック
    10桁数字か? 改行混入? → NG なら即返却
  • access_tokenaccess_token = LINE が発行する "代理メッセージ送信権"。 これを使って Skel·EC が サロン名義で メッセージを送れる。 つまり これが正しくないと 友だちに何も送れない。 有効性チェック
    LINE API GET /v2/bot/info に問い合わせ → 200 OK 返ってこなければ token 無効 / 期限切れ と判定 → 保存せずエラー報告
  • Stripe skStripe sk (Secret Key) = Stripe の "サロン専用 鍵"。 sk_live_xxxxx で始まる文字列。 これで Skel·EC が サロン名義で 決済を作れる。 漏れたら 別人が決済できちゃうので 厳重管理。 有効性チェック
    Stripe API accounts.retrieve に問い合わせ → エラー返れば sk 無効と判定
  • 同じ slug の tenant が既に存在しないか確認
    他のサロンと slug 衝突したら、 サロン名変更を促す

全部 OK の時だけ、 ようやく Firestore tenant doc 作成 + LINE/Stripe 設定の自動登録 に進みます。 バリデーション失敗時は 何も保存せず、 何を直すべきか具体的に オーナーに返却。

🛡️

このシステムは安心して 複数サロンに販売できます

Firestore のテナント分離、 LINE 署名検証、 Stripe メタデータ強制、 Firestore ルール、 4層の物理分離で データの混ざりは 絶対起きません。 セットアップエラーは個別に検知 + べき等で何度でもやり直し可能。 同じ仕組みで FP Compass が半年無事故稼働中 の実績あり。
